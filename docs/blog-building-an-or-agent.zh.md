# 构建 OR 智能体：从 ML-Intern 到领域专用 AI

## 为什么选择运筹学？

运筹学中有一个奇特的悖论。数学是优雅的——线性规划、对偶理论、网络流——但工具链却是残酷的。要解决一个真实的优化问题，你需要：

1. 阅读业务描述（"我们有 3 个仓库、5 个客户，最小化运输成本"）
2. 将其数学化（决策变量、目标函数、约束条件）
3. 转换为求解器特定的代码（Pyomo、cvxpy、GAMS）
4. 解释结果（影子价格、约减成本、灵敏度分析）
5. 向非技术利益相关者解释

步骤 1→3 是大多数人卡住的地方。不是因为数学很难——而是从"业务问题"到"数学模型"的转换需要多年练习才能掌握的思维跳跃。一个初级工程师可能需要一整天来建模，而一个有经验的运筹学从业者只需 10 分钟。

这正是 LLM 应该擅长的任务类型。知识存在于训练数据中——教科书、Stack Overflow、运筹学论坛。推理是有结构的——存在清晰的模式（最小化成本，受限于容量约束）。输出是明确定义的——一个包含变量、约束和目标函数的 Pyomo 模型。

但在"生成一些代码"和"解决真实问题"之间存在差距。单次 LLM 调用可以生成一个模型，但它无法：
- 验证模型的正确性
- 为问题类型选择合适的求解器
- 检测不可行性并建议重新建模
- 为业务背景解释灵敏度结果

这正是智能体能填补的鸿沟。不是单次 LLM 调用，而是一个协调的工作流，配备专用工具、质量门和迭代优化。

## ML-Intern 给了我们什么

我们不是从零开始。ML-Intern 是一个为机器学习任务构建的开源 AI 智能体框架。它提供了每个智能体都需要的基础设施：

- **智能体循环**：编排 LLM 调用、工具执行、用户交互和错误恢复的事件循环
- **上下文管理器**：当对话超出 LLM 上下文窗口时自动压缩
- **死循环检测**：防止智能体无限重试同一个失败操作
- **审批策略**：需要人工确认昂贵或危险操作的安全系统
- **会话持久化**：保存对话轨迹用于调试和重放

从头构建这些基础设施需要 3-4 个月。Fork 它并适配到运筹学只花了 2 周。

但"适配"低估了工作量。每一层都需要修改——有些是表面的，有些是根本性的。

## 6 阶段工作流：设计思考

### 核心设计理念

OR-Intern 采用六阶段质量门工作流，基于对运筹学问题特征的深刻理解而设计：

```
阶段 1: 建模     → 生成数学模型
阶段 2: 求解     → 选择求解器并执行
  ┌── 质量门 ──┐
  │ OPTIMAL, gap≈0 │→ 继续阶段 3
  │ gap>5% / 慢   │→ 尝试 compare_solvers（最多 3 次）
  │ INFEASIBLE    │→ 诊断不可行性，建议修复
  └──────────────┘
阶段 3: 验证  → 验证约束满足
阶段 4: 分析  → 灵敏度分析（影子价格、约减成本）
阶段 5: 可视化 → 生成图表
阶段 6: 报告  → 创建综合报告
```

### 为什么是质量门迭代？

运筹学问题有明确的成功标准：求解器找到最优解（gap = 0）或者没有。一旦获得最优解，进一步迭代毫无意义。因此，我们采用**质量门迭代**策略：

- 当解质量不可接受时迭代
- 当解质量达到阈值时停止
- **始终完成完整的分析流水线**

### 质量门逻辑

质量门位于阶段 2（求解）和阶段 3（验证）之间：

- **OPTIMAL 且求解时间 < 5s**：直接进入阶段 3-6
- **Gap > 5% 或求解时间 > 60s**：尝试 `compare_solvers` 测试 HiGHS、SCIP 和 Gurobi（如果可用）。如果仍然次优，尝试调整求解器参数。最多 3 次改进尝试后，继续执行。
- **INFEASIBLE 或 UNBOUNDED**：使用 `sensitivity_analysis` 诊断约束冲突。建议约束松弛或模型修复。**不要进入报告阶段**——没有有效解可以报告。
- **可行解存在**：始终完成阶段 3-6。用户期望完整的分析，而不仅仅是一个数字。

### 为什么不直接"遵循最佳实践"？

为什么要将此编码为硬性工作流，而不是告诉 LLM"遵循运筹学最佳实践"？

因为 LLM 是优化器。它们会选择到达"足够好"答案的最短路径。没有明确的阶段结构，LLM 会生成模型、运行它并报告结果——跳过验证、灵敏度分析和可视化。从 LLM 的角度来看，这些额外任务没有即时收益。

6 阶段工作流是一个**承诺装置**。它强制 LLM 完成那些区分"一个数字"和"一个答案"的工作。

明确的指令**"求解后不要停止！用户期望完整的分析"**是关键修复。没有它，即使是 6 阶段的提示词也会在实践中退化为 3 阶段。

## 挑战与解决方案

### 挑战 1：代码中的数学符号

LLM 在自然语言和代码上训练，但运筹学建模处于两者的交汇点。一个 Pyomo 约束如：

```python
model.c1 = Constraint(expr=model.x[1] + model.x[2] <= 10)
```

是代码，但其背后的推理是数学的。LLM 需要理解 "x₁ + x₂ ≤ 10" 转换为 `model.x[1] + model.x[2] <= 10`——并且不等号的方向很重要。

**解决方案**：我们添加了 `model_checker` 作为求解前验证工具。它检查：
- 约束中引用的所有变量都已声明
- 约束方向正确（<= vs >=）
- 目标函数引用有效变量
- 求解器与问题类型兼容

这在求解尝试之前捕获了许多错误，节省时间并防止令人困惑的错误消息。

### 挑战 2：不可行性诊断

不可行模型意味着"没有解满足所有约束"。这是常见的用户错误——他们过度约束了问题。但原始求解器输出只说"INFEASIBLE"，没有任何解释。

**解决方案**：当质量门检测到不可行性时，智能体进入诊断循环：
1. 逐个移除约束以找到最小不可行子集
2. 报告哪些约束冲突
3. 建议松弛（例如，"约束 c3 和 c5 冲突——尝试将 c5 从 <= 松弛为 <="）

这需要 `solve_job` 中的自定义逻辑，超出了标准求解器输出的范围。

### 挑战 3：上下文窗口管理

运筹学问题生成结构化输出——模型代码、求解器日志、灵敏度表、验证结果。单次求解可以产生 10,000+ 字符的输出。经过多轮对话，这会快速填满上下文窗口。

**解决方案**：我们针对运筹学特定模式调整了上下文管理器：
- **更低的阈值（85%）**：运筹学对话比一般聊天生成更多结构化输出
- **更小的每消息上限（30k 字符）**：求解器输出可能非常长
- **更大的尾部保留（10 条消息）**：最近的工具输出对 LLM 的推理至关重要
- **求解日志摘要**：将冗长的求解器输出压缩为结构化摘要（状态、gap、时间、关键变量）

## 试用

```bash
git clone https://github.com/or-intern/or-intern.git
cd or-intern
uv sync
cp .env.example .env  # 添加你的 API 密钥
uv run or-intern "Maximize 5x + 3y subject to 2x + y <= 20, x + 3y <= 30"
```

智能体将引导你完成：模型生成 → 求解器选择 → 解验证 → 灵敏度分析 → 可视化 → 报告。
